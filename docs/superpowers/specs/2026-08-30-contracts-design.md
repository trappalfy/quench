# Подпроект 1: Контракты и деплой

**Дата:** 2026-08-30
**Статус:** на ревью
**Чейн:** Robinhood Chain, chainId 4663
**Зависимости:** нет. Это фундамент — подпроекты 2, 4, 5, 6 читают эти контракты.

---

## 1. Цель

Задеплоить набор контрактов, позволяющий любому создателю выпустить токен с фиксированным предложением за неизменяемым Uniswap v4 хуком, поведение которого собрано из пяти блоков и полностью читаемо из чейна до первой сделки.

Область подпроекта заканчивается на задеплоенных и верифицированных контрактах с полным набором тестов. UI, слой чтения и индексер — другие подпроекты.

---

## 2. Проектные ограничения

Приняты как решения, а не как пожелания. Каждое проверяется тестом.

**2.1. Формального аудита в v1 нет.** Вместо него — ограничивающий ущерб дизайн (раздел 3), инвариантный фаззинг (раздел 8) и порог пересмотра (раздел 10).

**2.2. Кастодия сведена к трём местам, и каждое обосновано.**
`PotVault` держит котёл — иначе накопительный приз невозможен. `BondingCurve` держит собранный ETH до градации — по определению механики. `Launchpad` держит LP-позицию — в этом и смысл замка ликвидности.

Всё остальное, включая сам хук, кастодии не имеет: срезы рассчитываются и выплачиваются в той же транзакции. Ни один из трёх кастодиальных контрактов не имеет функции произвольного вывода средств.

**2.3. Хук неизменяем.** После привязки к пулу его нельзя ни заменить, ни перенастроить. Параметры фиксируются при инициализации пула.

**2.4. Апгрейдов нет.** Ни proxy, ни `delegatecall`, ни admin-функций, меняющих поведение. Новая версия — это новый деплой и новый реестр.

---

## 3. Дизайн, ограничивающий ущерб

Четыре решения, снижающие цену ошибки. Они архитектурные: добавить их позже будет дороже, чем заложить сразу.

**3.1. У хука нулевой баланс, всегда.**
LP Rewards выплачиваются через `poolManager.donate()` в той же транзакции — кастодии нет. Auto Burn отправляет токены на адрес сжигания немедленно — кастодии нет. Котёл Nth-buy живёт в отдельном контракте `PotVault`, а не в хуке.

Инвариант: `address(hook).balance == 0` и `token.balanceOf(hook) == 0` после любой транзакции.

**3.2. `PotVault` предельно мал.**
Ровно три функции: принять ETH с пометкой пула, выплатить победителю, прочитать баланс. Писать в него может только хук. Контракт достаточно мал, чтобы проверяться чтением.

Инвариант: `address(potVault).balance == сумма potBalance по всем пулам`.

**3.3. Потолок пула в первых версиях.**
`maxPoolEthWei` — иммутабельный параметр лаунчпада. Запуск с бóльшим объёмом отклоняется. Ограничивает максимальный ущерб от неизвестной пока ошибки. Снимается новым деплоем после прохождения порога из раздела 10.

**3.4. Средства протокола отделены.**
Комиссии протокола накапливаются на отдельном адресе и никогда не смешиваются с ликвидностью пулов или котлом.

## 4. Состав контрактов

| Контракт | Назначение | Кастодия |
|---|---|---|
| `LaunchToken` | ERC20, фиксированное предложение | нет |
| `BlockHook` | Uniswap v4 хук, пять блоков | нет |
| `PotVault` | Котёл Nth-buy | **да** |
| `Launchpad` | Фабрика, реестры, роялти, держатель LP | LP-позиция |
| `BondingCurve` | Кривая из 10 траншей и градация | ETH до градации |
| `BoundedRouter` | Канонический получатель, границы проскальзывания | нет |

### 4.1. `LaunchToken`

Предложение ровно `1_000_000_000e18`, минтится целиком лаунчпаду в конструкторе. Нет `owner`, нет `mint`, нет `pause`, нет чёрных списков, нет комиссии на трансфере. `name` и `symbol` иммутабельны, `decimals` равен 18.

За основу — Solady `ERC20`. Ничего не переопределяем.

### 4.2. `BlockHook`

Разрешения хука: младшие 14 бит адреса должны равняться `0x28CC`.

| Бит | Флаг | Зачем |
|---|---|---|
| 13 | `BEFORE_INITIALIZE` | валидация конфига, запрет чужих пулов |
| 11 | `BEFORE_ADD_LIQUIDITY` | только лаунчпад добавляет ликвидность |
| 7 | `BEFORE_SWAP` | динамическая комиссия, анти-снайп, ETH-срезы |
| 6 | `AFTER_SWAP` | сжигание доли токен-выхода |
| 3 | `BEFORE_SWAP_RETURNS_DELTA` | забрать ETH-срез из входа |
| 2 | `AFTER_SWAP_RETURNS_DELTA` | забрать токен-долю из выхода |

Адрес достигается майнингом соли под CREATE2 (раздел 7).

**Конфигурация на пул**, задаётся один раз в `beforeInitialize`:

```solidity
struct BlockConfig {
    // Блок 1 - Anti-Snipe
    uint32  guardBlocks;      // длина окна защиты в блоках
    uint16  maxBuyBps;        // потолок покупки, bps от резерва пула
    uint24  snipeTaxPips;     // надбавка к LP-комиссии внутри окна
    // Блок 2 - Surge Fees
    uint24  baseFeePips;      // базовая комиссия
    uint24  maxFeePips;       // потолок комиссии
    uint16  surgeSens;        // чувствительность к глубине
    // Блок 3 - Auto Burn
    uint16  burnBps;          // доля токен-выхода в сжигание
    uint128 burnTriggerWei;   // минимальная покупка для срабатывания
    // Блок 4 - LP Rewards
    uint16  lpBps;            // доля ETH-входа в пользу LP
    // Блок 5 - Nth-buy Pot
    uint16  potBps;           // доля ETH-входа в котёл
    uint16  potEveryN;        // платим каждой N-й квалифицирующей покупке
    uint128 potMinBuyWei;     // минимальная покупка для участия
}
```

Блок считается выключенным, когда его параметры нулевые. Пять блоков — это не пять контрактов, а пять групп полей в одной структуре.

**Состояние на пул:**

```solidity
struct PoolState {
    uint64  startBlock;        // блок инициализации пула
    uint128 potBalance;        // учёт котла, средства лежат в PotVault
    uint32  potBuyCount;       // публичный счётчик
    uint64  lastCountedBlock;  // счётчик двигается не чаще раза в блок
}
```

### 4.3. `PotVault`

```solidity
function fund(PoolId id) external payable;         // только хук
function pay(PoolId id, address to, uint256 amt);  // только хук
function balanceOf(PoolId id) external view returns (uint256);
```

Никаких других функций. Нет вывода владельцем, нет аварийного слива.

### 4.4. `Launchpad`

Фабрика, реестр запусков, реестр блупринтов, расчёт роялти, держатель LP-позиции.

```solidity
function launchInstant(InstantParams p) external payable returns (address token);
function launchCurve(CurveParams p) external payable returns (address token);
function publishBlueprint(BlockConfig cfg, uint16 royaltyBps) external returns (uint256 id);
function claimFees(address token) external;

function launchCount() external view returns (uint256);
function tokenAt(uint256 i) external view returns (address);
function launchRecord(address token) external view returns (LaunchRecord);
function blueprintCount() external view returns (uint256);
function blueprintAt(uint256 i) external view returns (Blueprint);
```

LP-позиция удерживается контрактом, **функция вывода отсутствует физически**. Комиссии собираются, тело позиции — нет.

Распределение комиссий: доля создателя задаётся при запуске (по умолчанию 50%, потолок 80% на ETH-ноге), токенная сторона сжигается, роялти автору блупринта отчисляется из ETH-доли.

### 4.5. `BondingCurve`

80% предложения продаётся десятью траншами по 80 миллионов токенов. Цена транша с номером `i` (нумерация с нуля) равна `p0 * 1.7^i`. Комиссия 1% с каждой сделки, поровну создателю и протоколу.

Полный сбор при распродаже всех траншей:

```
ETH = 80_000_000 * p0 * сумма(i=0..9) 1.7^i = 80_000_000 * p0 * 286.6
```

Градация происходит в той же транзакции, что и покупка последнего транша: собранный ETH и оставшиеся 20% предложения становятся full-range позицией Uniswap v4 по цене `p0 * 1.7^9`, с привязанным хуком и динамической комиссией.

Степени 1.7 считаются по предвычисленной таблице из десяти констант, а не возведением в степень в рантайме. Точность фиксируется тестом.

### 4.6. `BoundedRouter`

Обязателен: хук требует канонического ненулевого получателя для квалификации покупки в Nth-buy Pot, а стандартный Universal Router его не подставляет. Без своего роутера пятый блок не работает.

Дополнительно несёт границы проскальзывания и дедлайн. Собственного баланса не имеет.

## 5. Формулы

Единый источник истины. Слой чтения и симулятор в UI обязаны воспроизводить их точно — это проверяется дифференциальным тестом из раздела 8.

Во всех формулах `inRangeReserve` означает ETH-сторону ликвидности, активной в текущем диапазоне цены. Единая величина для всех блоков — отдельного «резерва пула» в расчётах нет.

**Anti-Snipe** — внутри окна `block.number < startBlock + guardBlocks`:

```
require(amountIn <= inRangeReserve * maxBuyBps / 10_000)
feePips += snipeTaxPips
```

**Surge Fees:**

```
depthBps    = amountIn * 10_000 / inRangeReserve
surgeFactor = min(depthBps * surgeSens / 10_000, 10_000)
feePips     = baseFeePips + (maxFeePips - baseFeePips) * surgeFactor / 10_000
```

**LP Rewards** — только exact-input покупки:

```
lpCut = amountIn * lpBps / 10_000
poolManager.donate(key, lpCut, 0)
```

**Nth-buy Pot** — только exact-input покупки:

```
potCut = amountIn * potBps / 10_000
potVault.fund{value: potCut}(id)

если amountIn >= potMinBuyWei и block.number > lastCountedBlock:
    potBuyCount += 1
    lastCountedBlock = block.number
    если potBuyCount % potEveryN == 0:
        potVault.pay(id, recipient, potBalance)
```

**Auto Burn** — только exact-input покупки, при `amountIn >= burnTriggerWei`:

```
burnAmount = tokenOut * burnBps / 10_000   -> на адрес сжигания
```

**Полная стоимость покупки** — то, что показывает симулятор:

```
ETH-сторона:    feePips/1e6 + lpBps/1e4 + potBps/1e4
токен-сторона:  burnBps/1e4
```

Продажи и exact-output покупки платят только LP-комиссию, никаких срезов.

## 6. Валидация в `beforeInitialize`

Пул не создаётся, если хоть одно условие нарушено.

| Условие | Причина |
|---|---|
| вызывающий — `Launchpad` | иначе появятся чужие пулы с нашим хуком |
| `baseFeePips <= maxFeePips <= 100_000` | потолок комиссии 10% |
| `lpBps + potBps <= 1_000` | суммарный ETH-срез не выше 10% |
| `snipeTaxPips <= 50_000` | надбавка не выше 5% |
| `burnBps <= 1_000` | сжигание не выше 10% |
| `guardBlocks <= 7_200` | окно не длиннее примерно суток |
| `potEveryN` в диапазоне `[2, 1_000]` | вне диапазона котёл бессмыслен |
| `potBps > 0` требует `potEveryN >= 2` | согласованность блока |
| `maxBuyBps` в `[1, 10_000]` при `guardBlocks > 0` | согласованность блока |
| `burnBps > 0` требует `burnTriggerWei > 0` | иначе сжигание на пылевых сделках |

## 7. Деплой

Порядок: `PotVault`, затем майнинг соли, затем `BlockHook` через CREATE2, затем `Launchpad`, `BondingCurve`, `BoundedRouter`, затем связывание адресов.

Майнинг соли использует `HookMiner` из v4-periphery: перебор солей до адреса, у которого младшие 14 бит равны `0x28CC`. Ожидаемое число попыток — порядка 16 тысяч, то есть секунды работы.

CREATE2-фабрика — канонический детерминистический деплойер `0x4e59b44847b379578588920cA78FbF26c0B4956C`. Его наличие на чейне 4663 проверяется скриптом до начала работы; при отсутствии деплоим свою.

Известные адреса чейна:

| Что | Адрес |
|---|---|
| Uniswap v4 PoolManager | `0x8366a39CC670B4001A1121B8F6A443A643e40951` |
| RPC мейннет | `https://rpc.mainnet.chain.robinhood.com` |
| RPC тестнет (46630) | `https://rpc.testnet.chain.robinhood.com` |

Разработка ведётся против форка мейннета через `anvil --fork-url`. Боевой деплой идёт в мейннет, промежуточного тестнета в маршруте нет.

## 8. Тестирование

**Юнит-тесты** — каждый блок изолированно, включая границы валидации и все ветки отказа.

**Интеграционные** — на форке мейннета с настоящим PoolManager: полный цикл запуска через кривую, градация, торговля после градации.

**Инвариантный фаззинг** — заменяет собой аудит, поэтому список инвариантов является частью спеки:

1. `address(hook).balance == 0` после любой последовательности операций
2. `token.balanceOf(hook) == 0` для любого токена
3. `address(potVault).balance` равен сумме `potBalance` по всем пулам
4. сумма всех срезов в свопе не превышает `amountIn`
5. `potBuyCount` растёт не более чем на 1 за блок на пул
6. выплата котла не превышает его накопленного баланса
7. сжигание уменьшает выход получателя, но никогда не резервы пула
8. у `Launchpad` нет пути исполнения, уменьшающего тело LP-позиции
9. сумма выплаченных комиссий не превышает собранных
10. после градации конфиг хука для пула не меняется ни одним вызовом

**Дифференциальный тест** — расчёт стоимости покупки в TypeScript (для симулятора в UI) обязан совпадать с ончейн-расчётом на случайных входах. Гарантирует, что интерфейс не врёт про цену.

## 10. Порог пересмотра решения по аудиту

Формальный аудит заказывается при наступлении **любого** из событий:

- суммарный TVL в пулах лаунчпада превышает порог, согласуемый до боевого деплоя
- появляется первый запуск, созданный не владельцем проекта
- снимается ограничение `maxPoolEthWei` из пункта 3.3

До этого момента интерфейс обязан явно сообщать, что контракты аудит не проходили.
